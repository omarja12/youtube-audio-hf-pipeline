01 / THE PROBLEM

Bulk downloads fail quietly.

YouTube can return the same “Video unavailable” message for a deleted video and a temporary rate limit. A long-running job can look healthy while silently producing a smaller dataset than expected.

This project treats reliability as a data-quality problem. It classifies failures conservatively, stops when the connection is blocked, and remembers only outcomes that are genuinely safe to make permanent.

02 / THE DESIGN

Progress becomes permanent
only after the commit.

DOWNLOAD→PACKAGE→UPLOAD→COMMIT→RECORD

Work is grouped into small, restartable batches. The running metadata file is updated only after a Hugging Face commit lands. If the process stops, the next run can redo one group without corrupting the dataset or losing track of what is already there.

03 / ENGINEERING DECISIONS

Small decisions with large consequences.

A

Retry by default

Unknown errors are retried. A needless retry costs seconds; a false permanent failure can remove good data forever.

B

Subprocess isolation

yt-dlp runs outside the orchestrator, keeping crashes and JavaScript runtime configuration at the boundary where they belong.

C

Rate limits are a circuit breaker

When the remote service pushes back, the run stops with progress saved instead of turning throttling into more bad data.

D

The laptop stays awake

Windows power state is managed for the process duration, without changing the machine’s global power plan.
